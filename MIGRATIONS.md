# Migrating an existing app to `mob_mishka`

If your app was generated by `mix mob.new` before mob_new 0.5.x, it
carries a vendored copy of ~75 Mishka composites under
`lib/<app>/components/mishka_*.ex`, a fenced
`config :mob, :extra_tags` block in `config/config.exs`, and a
`<App>.Showcase.register_all()` call in `on_start`. Once you depend
on the `mob_mishka` plugin, most of that is redundant.

There are three shapes an existing app can take:

1. **Depend on the plugin, keep the vendored files** — nothing
   breaks. The plugin's composites and your app-local copies both
   register with `Mob.Composite`, and the app-local ones win by
   virtue of being registered later (or, once you set
   `config :mob_mishka, :override_namespace, <App>.Components`, by
   the plugin's explicit override lookup at boot). This is the
   safest transitional state.

2. **Depend on the plugin, delete the vendored files that never
   changed, keep the ones you edited** — the shape this guide
   produces. Regenerating an app never re-clobbers your edits, and
   the plugin's default handles everything else.

3. **Depend on the plugin, delete ALL vendored files** — for apps
   with no local edits. `mix mob_mishka.gen <name>` re-ejects an
   individual composite whenever you want to edit one.

## The migration task

`mix mob_mishka.migrate` does the analysis and (with `--apply`) the
cleanup. Default is a dry run:

```
$ mix mob_mishka.migrate
Planned migration:

  [remove]   lib/my_app/components/mishka_avatar.ex  (matches plugin's :mishka_avatar)
  [remove]   lib/my_app/components/mishka_chip.ex    (matches plugin's :mishka_chip)
  [keep]     lib/my_app/components/mishka_dialog.ex  (edited copy; supersedes plugin's :mishka_dialog at boot)
  [skip]     lib/my_app/components/mishka_custom.ex  (no matching plugin composite)
  [strip*]   config/config.exs                        (compat bridge; needs --remove-extra-tags to strip)

Dry run — no files written. Re-run with `--apply` to make these changes.
```

Apply the changes with `--apply`:

```
$ mix mob_mishka.migrate --apply
```

Vendored copies that are byte-identical to the plugin's default (after
normalising the `<App>.Components.*` vs `MobMishka.Components.*`
namespace substitution `mob_new` performs on generation) are deleted.
Edited copies stay on disk and continue to supersede the plugin's
default once you set:

```elixir
# config/config.exs
config :mob_mishka, :override_namespace, MyApp.Components
```

## The `extra_tags` compatibility bridge

The fenced `config :mob, :extra_tags` block in `config/config.exs` is
a **compatibility bridge**. It keeps the `~MOB` sigil silent about
`<MishkaChip />` and friends when your app runs on a mob release that
predates plugin-manifest tag discovery (MOB-247). Once your app's
`mob` dep is on a release that ships MOB-247, the plugin's own
`priv/mob_plugin.exs` supplies the whitelist and the block is dead
code that goes stale on every plugin release.

Strip it with:

```
$ mix mob_mishka.migrate --apply --remove-extra-tags
```

Only pass `--remove-extra-tags` **after** you've verified your mob dep
is past MOB-247. Otherwise you'll get a wall of `~MOB: <MishkaChip>
is not in the Mob tag whitelist` warnings on the next `mix compile`.

## Editing a composite after migrating

Once vendored copies are gone, `mix mob_mishka.gen <name>` ejects a
specific composite into your app's `lib/<app>/components/` for
editing:

```
$ mix mob_mishka.gen dialog
* creating lib/my_app/components/mishka_dialog.ex
```

Ensure the override namespace is set (once, per app):

```elixir
# config/config.exs
config :mob_mishka, :override_namespace, MyApp.Components
```

Edit `lib/my_app/components/mishka_dialog.ex` however you like. On
the next boot, the plugin's registry sees `MyApp.Components.MishkaDialog`
and prefers it over the plugin's shipped `MobMishka.Components.MishkaDialog`
for the `:mishka_dialog` tag.

Delete the ejected file to revert to the plugin's default. The
override lookup falls back cleanly.

## Rolling back

If the migration causes a regression, `git checkout` the deleted
files and the app is back to the pre-migration shape. The plugin dep
doesn't have to come off — you can run in state (1) indefinitely.
