## What this repo is

A Hex plugin that ships 73 Mishka Chelekom composites for Mob apps, replacing the "vendor 75 composite files into every generated app" pattern that `mob_new` used before MOB-252. Depend on it in an app's `mix.exs` (`{:mob_mishka, "~> 0.1"}`), activate in `mob.exs` (`config :mob, :plugins, [:mob_mishka]`), and every `<Mishka…>` composite works in your `~MOB` sigils.

Upstream design system is Mishka Chelekom's Phoenix side at [mishka-group/mishka_chelekom](https://github.com/mishka-group/mishka_chelekom) (Shahryar Tavakkoli / [@shahryarjb](https://github.com/shahryarjb)). Visual and prop parity is a goal; code parity is not — the mob composites use `Mob.Canvas` / `Mob.UI` primitives, not Phoenix HTML/CSS. See AGENTS.md § "Relationship to mishka_chelekom" for the split.

## Worktrees

**Default assumption: work happens in a git worktree.** Multiple agents may be running in parallel; each task in its own worktree prevents conflicts between agents and keeps `master` clean while work is in flight.

If you're assigned a task and worktree usage isn't mentioned, ask:

> "Should I use a worktree for this?"

Yes for anything non-trivial or that touches templates. In-place is fine for a single-file doc edit, one-line config change, or a version bump.

```bash
cd ~/code/mob_mishka
git worktree add ../mob_mishka-worktrees/<slug> -b <branch>
cd ../mob_mishka-worktrees/<slug>
```

If the user explicitly says "use worktrees" up front, do so without asking. The git stash stack is shared across worktrees — never use bare `git stash` / `git stash pop`.

## Building and running locally

```bash
cd ~/code/mob_mishka
mix deps.get
MIX_ENV=test mix test              # composite unit tests + doctests
mix docs                            # build HexDocs locally at doc/index.html
```

There's no on-device build step in this repo — mob_mishka is pure Elixir. To actually see a composite render, you use it in a Mob app (e.g. an app generated by `mix mob.new` that pulls this plugin as a dep) and deploy that app to a device. See "Physical-device verification" in AGENTS.md.

## Pre-commit checklist

Before committing changes, run **all** in this order:

```bash
mix test                            # full suite must pass
mix format                          # apply Elixir formatting
mix credo --strict                  # whole tree, includes ExSlop AI-pattern checks
```

Pre-push hook (`.githooks/pre-push`) adds format + `mix test --exclude macos_only --exclude requires_zig` on every push. Activate once per clone or worktree:

```bash
git config core.hooksPath .githooks
```

### Tests are part of the change, not a follow-up

New behaviour ships with a test unless the change is small enough that a test would only restate it — a rename, a doc string, a formatting pass. "I'll add coverage later" is how the untested paths in this repo got there.

The bar is not coverage percentage, it is: **would this test fail if the fix were reverted?** Check by reverting it. A test that passes either way is worse than none, because it is claimed as evidence.

### Decision log — check both directions

Before committing, ask two questions, not one.

**Does this need a new record?** Anything non-obvious: a tradeoff, a workaround, a convention, a "why X and not Y". The test is whether a reader six months from now would ask why it is like this. If the commit message is explaining a decision, that decision belongs in `decisions/` where it is findable, not only in `git log`. Record it in the same commit, not as a follow-up.

**Does this INVALIDATE an existing record?** This is the half that gets missed, and it is the more dangerous one. A record asserting a property the code no longer has is worse than no record: it is a claim a maintainer will act on. Grep `decisions/` for the mechanism you are changing before you commit.

When you correct a record, correct it **in place** with a note saying what was wrong, rather than quietly deleting the claim. The wrong version is the part a future reader needs to recognise, and `decisions/` is append-only for superseding whole decisions, not for silently editing away a mistake inside one.

### Adversarial review — before the commit, by a subagent

**Non-trivial work gets an adversarial review before it is committed.** Spawn a subagent, point it at the actual diff, and tell it to find defects rather than to approve. Act on what it finds, then commit.

It must be a **separate agent**, not a re-read of your own work. The thing that is wrong is usually the author's mental model of the change, and that model is exactly what a self-review carries into the second pass.

Give the reviewer: the diff to read (`git diff <base>..HEAD`, and the base explicitly, since a diverged local branch will otherwise sweep in the whole tree), what the change claims to do, and the specific things you are least sure about. Tell it to cite `file:line` for every finding, rank them blocking / should-fix / nitpick, and separate what it verified in source from what it is reasoning about platform semantics.

Skip it for mechanical or trivial changes: formatting, a typo, a version bump, a changelog edit, moving a file. Reach for it when the change has behaviour, touches a canvas op, or spans a platform boundary.

Recent example this discipline caught: [MOB-256](https://github.com/GenericJam/mob_new/pull/75), an Android canvas rendering bug that this plugin's `MishkaSemiCircleProgress` and `MishkaAngleSlider` surfaced. Three plausible-looking "fixes" (clip-only, sweep-negate, start/end-swap) went through before an adversarial review of the wrong-answer diffs redirected to the actual root cause (dp→px scaling of angle values in mob_new's generated Android bridge). Each wrong fix would have shipped without the review.

### Before the merge — a second review, on the PR

The pre-commit review reads a diff. This one reads a diff that claims to be finished, against a master that has moved since you started. Those are different questions, and the second one has caught more.

Give the reviewer the PR, what it claims, and what you are least sure of, and ask for a verdict — MERGE or DO NOT MERGE, with reasons. Then act on it. A review you overrule is fine if you say why; a review you skip because the work felt done is the case this exists for.

**Check the mechanical preconditions yourself; do not delegate them:**

- **CI is green AND the run is newer than the last commit.** A green check from before your latest push proves nothing.
- **The branch is not behind master.** The `pre-push` hook says how far.
- **Cross-repo claims are true now, not eventually.** Documentation that names a sibling's version — "requires mob 0.9.0" — is false until that version exists on Hex. Land the sibling first, or make the claim true in the same session.

### Trust the instrument last

Every rung of the fidelity ladder assumes the thing measuring is honest. When it is not, the failure does not look like an error — it looks like a result.

- **A number better than the theory allows is a bug in the measurement.**
- **Make a probe fail loudly when its own precondition does not hold.** A check that silently passes when the setup did not happen is worse than no check.
- **Corroborate against something you did not build.** Screenshot from a device, `Mob.Test.assigns/1` state, `logcat` output — agreement with an independent source is evidence; your own instrument agreeing with itself is not.
- **When you publish a number that turns out wrong, retract it in place** and say what was wrong. Someone will otherwise act on it.

## Release flow

Canonical process lives in [`~/code/mob/RELEASE.md`](../mob/RELEASE.md) — trigger model (mix.exs as source of truth), patch-bump default, CHANGELOG conventions, per-step idempotency of `release.yml`.

> **Review gate is on by default.** Everything that landed since the last published version gets a code review *before* you publish — scoped at `v<last-published>..HEAD`, not per-PR — plus the version-sanity checks (is this version already published? did anything merge after the bump commit?). Skip only if the user says so.
>
> **mob_mishka's `mob` floor pin is load-bearing.** Every release must state the mob version it needs and pin its `mob` dep accordingly. When a composite here relies on a new `Mob.Canvas` op or a new `Mob.Sigil` semantic, land it in mob, wait for its release, then bump this pin — do not ship a plugin release that depends on an unreleased mob feature.
>
> **Lockstep with mob for user-visible feature releases.** New composite that requires a new `~MOB` tag semantics feature in mob → publish mob first, then this plugin against the released mob, then bump `mob_new`'s pins.

**Trigger:** Push a commit that modifies `mix.exs` (with the `@version "X.Y.Z"` attribute bumped) to master, and `.github/workflows/release.yml` tags it, creates the GitHub Release, and publishes to Hex — each step idempotent. The `HEX_API_KEY` secret needs to be set on the repo for the publish step; without it the workflow completes tag + release and skips Hex with a notice.

Manual re-runs (Actions tab → Run workflow) are safe — each step checks its own state and only does work that is missing.

## Connecting an IEx session to a running Mob app

Composite verification is fastest as an IEx round-trip: drive a screen using the composite, then read `Mob.Test.assigns/1` for state or `mob_nif:screenshot/3` for pixels. The full guide is at [`~/code/mob/CLAUDE.md`](../mob/CLAUDE.md) § "Connecting an IEx session". Short version:

```bash
cd /path/to/your_mob_app     # not this repo — a mob app that uses this plugin
mix mob.connect              # sets up tunnels, IEx attached to all connected devices
```

Then from any Mac-side IEx / one-shot script:

```elixir
node = :"your_app_android_<suffix>@127.0.0.1"
Node.connect(node)
:rpc.call(node, GenServer, :call, [:mob_screen, :get_current_module])
:rpc.call(node, Process, :send, [:mob_screen, {:tap, :your_tag}, []])
:rpc.call(node, :mob_nif, :screenshot, [:png, 90, 1.0])
```

For a composite that composes another, set an `:id` prop on the outer composite in your test screen so you can address it directly.

The `mishka_verify` scratchpad app under `~/code/mob_mishka/…` (or wherever you spun one up) is a common shape: `mix mob.new mishka_verify` with a local path dep on `mob_mishka`, then a home screen that shows each composite. Kept for MOB-256 verification; similar throwaway apps should be spun up per major cross-platform composite change.

## Decision log

Non-obvious decisions — tradeoffs, workarounds, conventions, "why we chose X over Y" — go in `decisions/`, **one file per decision**:

    decisions/YYYY-MM-DD-short-slug.md

Each file is a lightweight ADR:

    # <Title>
    - Date: YYYY-MM-DD
    - Status: accepted | superseded by <file> | proposed
    ## Context        — what prompted this
    ## Decision       — what we chose
    ## Consequences   — tradeoffs, follow-ups

**Append new files; never edit existing ones.** If a decision changes, add a new file and mark the old one `Status: superseded by <new-file>`. One file per decision keeps the log conflict-free across parallel agents/worktrees — the date-sorted directory listing is the index.
